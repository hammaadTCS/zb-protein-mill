# M3: Core entries

## T3.1 Rate pending and adding the rate later

**Goal:** record kg now, rate later, with a full history of rate changes.

**Client requirement:** F-09; D-09, D-10.

**Depends on:** T2.10.

**Build exactly:**
- `CreatePurchase` now accepts `rate = null`: `rate_status = pending`, `rate` and `amount` null, **no journal** (BR-PUR-04, BR-LED-06). "Paid now" is still allowed (its payment posts normally; the supplier shows an advance until the rate is added).
- Migration `create_rate_changes_table` per spec §9.5 with the `prevent_change()` trigger.
- Action `AddPurchaseRate(User, Purchase, string $rate, string $date)`:
  - only for `rate_status = pending` and `status = active`;
  - sets rate, amount, `rate_status = fixed`, `rate_fixed_at = now()`;
  - posts PR-01 with `posting_date` = the purchase's `entry_date` when that month is open; otherwise = `$date` (the day the rate is added, which must be in an open month) (BR-LED-08);
  - writes `rate_changes` (old_rate null, new_rate, old_amount null, new_amount) and audit `rate_added`.
- `Party::balance()->pendingKg` = sum of kg of the party's active pending purchases.
- `PartyKhata` shows pending rows (kg, "Rate pending", no amount).
- Route `POST /purchases/{id}/rate` (`purchase.update`), "Add rate" button and dialog on page 5.
- Page 26 `/rate-pending`: purchases with `rate_status = pending` (sales added in T3.4): voucher, date, party, item, kg, age in days (`Today − entry_date`), red when age > `rate_pending_age_days` (BR-CHK-05), "Add rate" inline.

**Rules:** BR-PUR-03 (pending part), BR-PUR-04, BR-PUR-09 (adding), BR-LED-06, BR-LED-08, BR-CHK-05.

**Tests (write first):**
- `T-05 a rate-pending purchase creates no journal and no balance change`.
- `T-05 adding the rate posts PR-01 and writes a rate_changes row`.
- `AT-1 #4 and #12`: Karim pending 400 kg, then rate 49 → amount 19600.00; Karim "We owe 38400.00" (after #2's 18800.00).
- `BR-LED-08 rate added in February for a January entry in a closed January posts on the February date` (use `closeMonthForTest('2026-01')`, today 2026-02-05).
- `BR-CHK-05 an entry 8 days old is flagged when the limit is 7` (today 2026-02-05, entry 2026-01-28).

**Not in this task:** changing an existing fixed rate (T3.2), sales (T3.4).

**Done when:** tests pass.

## T3.2 Edit and cancel purchases

**Goal:** fix mistakes without ever deleting.

**Client requirement:** D-10, D-24.

**Depends on:** T3.1.

**Build exactly:**
- Action `UpdatePurchase`: any field except voucher number may change; the party must stay a supplier (BR-PTY-04). In one transaction: reverse the current journal (posting date = original posting date), apply changes, post a new PR-01 (posting date = new entry date), point `journal_entry_id` to the new journal (BR-PUR-11). A rate change on a fixed entry writes `rate_changes` and audit `rate_changed`. A pending entry edits without any journal. Audit `updated` with every changed field's old and new value.
- Optimistic lock (BR-GEN-09): the form sends `version` = the record's `updated_at` as ISO string; a mismatch throws the glossary "Concurrent edit" message (HTTP 409).
- Action `CancelPurchase(User, Purchase, string $reason, bool $cancelLinkedPayment)`: reason ≥ 5 characters (BR-GEN-04); reverse the journal (if any); status cancelled with reason, user and time; if `$cancelLinkedPayment`, cancel the "paid now" payment the same way (BR-PUR-12). Audit `cancelled`.
- Both refused when the entry date (or the journal's posting date) is in a closed month (BR-PUR-14) with the glossary "Closed month" text.
- Routes `GET /purchases/{id}/edit`, `PUT /purchases/{id}`, `POST /purchases/{id}/cancel`. Edit page reuses the create form. Cancel uses `ConfirmWithReason` with the checkbox "Also cancel the linked payment".
- Cancelled entries show the grey crossed-out "Cancelled" badge and stay in lists (filter "Cancelled").

**Rules:** BR-PUR-11, BR-PUR-12, BR-PUR-14, BR-GEN-03, BR-GEN-04, BR-GEN-09, BR-PUR-09 (changes).

**Tests (write first):**
- `T-06 editing kg reverses and reposts` (exact journals: original, reversal, new).
- `T-06 cancelling reverses the journal and keeps the row`.
- `BR-PUR-12 cancelling without the linked payment leaves an advance`.
- `BR-GEN-04 a 4-character reason is refused`.
- `BR-GEN-09 a stale version is refused`.
- `BR-PUR-14 a purchase in a closed month cannot be edited or cancelled`.
- `changing a fixed rate writes rate_changes with old and new values`.

**Not in this task:** the adjustment block on cancel (T4.6), rate corrections (T4.7).

**Done when:** tests pass.

## T3.3 Purchase warnings and weight-slip settings

**Goal:** catch typing mistakes and enforce the client's slip rules.

**Client requirement:** D-11, D-12, D-33; O-04, O-25, O-26.

**Depends on:** T3.2.

**Build exactly:**
- `GET /purchases/last-rate?party_id=&item_id=` → `{ rate, date }` of the latest active fixed purchase for that supplier and item, or null. Shown under the rate field as "Last rate: Rs 52.00 on 06-01-2026". **Never** prefilled (BR-PUR-05).
- Unusual rate (BR-PUR-06): average = weighted average (`Σ amount ÷ Σ kg`, spec §12.4) of the last `unusual_rate_lookback` active fixed purchases of the same item, all suppliers, by `entry_date` then id, excluding the entry being edited. When none exist, no warning. Warning `unusual_rate` when `|rate − average| ÷ average × 100 > unusual_rate_percent`. Message from glossary §4 (percent rounded to whole number, higher/lower). Checked on create, edit and add-rate.
- Duplicate entry (BR-PUR-08): warning `duplicate_entry` when another **active** purchase has the same party, item, kg and entry date (excluding itself).
- Slip settings (BR-PUR-07): `slip_no` required when `slip_no_required`; a slip photo attachment required when `slip_photo_required`; `our_weight_kg` refused (validation) when `plant_has_scale` is false, otherwise optional and > 0.
- Every confirmed warning writes audit `warning_confirmed`.

**Rules:** BR-PUR-05 to BR-PUR-08.

**Tests (write first):**
- `BR-PUR-05 last rate returns 52.00 for Aslam after AT-1 #10`.
- `BR-PUR-06 rate 70 against an average of 50 with limit 30% warns; confirmed it saves and logs`.
- `BR-PUR-06 rate 60 against 50 does not warn` (20%).
- `BR-PUR-06 weighted average uses the last 5 only` (create 6 purchases; the oldest must not count).
- `BR-PUR-08 same party, item, kg and date warns`.
- `BR-PUR-07 slip number required when the setting is on`; `our weight refused when plant has no scale`.

**Not in this task:** sales warnings (T3.4 reuses this code).

**Done when:** tests pass.

## T3.7 Payment approvals

**Goal:** large payments and first payments to new parties wait for the owner.

**Client requirement:** D-28; O-01, O-02.

**Depends on:** T3.6.

**Build exactly:**
- In `CreatePayment` and in "paid now" (BR-PUR-10), for direction `paid` created by a user **without** `payment.approve` (BR-USR-01):
  - pending when `amount ≥ payment_approval_limit` (BR-PAY-06); or
  - pending when the party has no earlier **posted** paid payment and `amount ≥ new_party_first_payment_limit` (BR-PAY-07).
- Pending payment: `approval_status = pending`, no journal, no balance change (BR-PAY-08). The response message is the glossary "Approval pending" text.
- Actions `ApprovePayment(User owner, Payment)` (posts; posting date = entry date, or today if that month is closed; audit `approved`) and `RejectPayment(User owner, Payment, reason)` (no journal; stays visible; audit `rejected`). Creator may edit or cancel while pending.
- Page 27 `/approvals`: pending payments, oldest first, with party balance, Approve and Reject (with reason). Owner only (`payment.approve`).
- Khata shows pending payments greyed, outside the balance.
- Receipts never need approval (BR-PAY-10).

**Rules:** BR-PAY-06, BR-PAY-07, BR-PAY-08, BR-PAY-10, BR-USR-01, BR-PUR-10 (approval part).

**Tests (write first):**
- `T-08 accountant payment of 60000 with limit 50000 is pending with no journal`.
- `T-08 owner payment of 60000 posts immediately`.
- `T-08 first payment rule`: limit 0 → accountant's first paid payment to a new party is pending; the second (after the first is approved) is not.
- `T-08 rejected payment never posts`.
- `BR-PAY-08 approval date rule when the entry month is closed`.
- `AT-4` from `docs/acceptance/controls.json` (run only this case).
