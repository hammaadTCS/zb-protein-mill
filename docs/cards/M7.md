# M7: Month-end and remaining controls

## T7.1 Month-end close (backend)

**Goal:** a month closes only when the books match the bank and the cash, then it is locked.

**Client requirement:** D-26, D-27.

**Depends on:** T6.10.

**Build exactly:**
- Migration `create_bank_reconciliations_table` per spec §9.5.
- Actions:
  - `RecordBankStatement(User, Period yyyymm, MoneyAccount bank, string $statementBalance)` — stores system balance (ledger, posting date ≤ last day) and difference.
  - `PostCashDifference(User owner, yyyymm, MoneyAccount cash, string $amount, string $direction shortage|excess, string $note)` — PR-23 or PR-24 dated the month's last day, voucher CSH, source `month_end_adjustment`; note required.
  - `CloseMonth(User, yyyymm, bool $acceptPendingRates)` running these checks in order and returning each check's pass/fail and details:
    1. previous months closed (BR-MEC-01; the first month is the month of `system_start_date`);
    2. rate-pending entries dated in the month → pass only when `$acceptPendingRates` (BR-MEC-02);
    3. no payment dated in the month awaiting approval (BR-MEC-03);
    4. trial balance as of the last day balanced (BR-MEC-04);
    5. `bank_match` for each active bank: latest statement for the month entered and equal to the **live** ledger balance at the last day (BR-MEC-05);
    6. `cash_match` for each active cash account: latest cash count dated the last day exists and its counted amount equals the **live** ledger balance at the last day (BR-MEC-06).
  - All pass → periods row `closed`, `closed_by`, `closed_at`; `period_events` row; audit `month_closed`. Any fail → nothing changes.
- From now on `closeMonthForTest()` must not be used by new tests.

**Rules:** BR-MEC-01 to BR-MEC-07; PR-23, PR-24.

**Tests (write first):** `AT-3` from `docs/acceptance/controls.json` (failing checks with exact differences, then the fixes, then closed, then the refused purchase); `BR-MEC-01 February cannot close before January`; `BR-MEC-02 pending rates block unless accepted`; `BR-MEC-03 awaiting approval blocks`.

**Done when:** tests pass.

## T7.2 Month-end pages and reopen

**Goal:** the owner closes a month step by step and can reopen the latest one with a reason.

**Depends on:** T7.1.

**Build exactly:**

- Page 31 `/months`: every month from the start month to the current month with status, closed by and date; "Reopen month" only on the latest closed month (`period.reopen`, reason required, BR-MEC-08); event and audit `month_reopened`.

**Rules:** BR-MEC-08; spec §11.12.

## T7.4 Merge duplicate parties

**Goal:** combine two profiles of the same person without rewriting history.

**Client requirement:** D-06.

**Depends on:** T7.3.

**Build exactly:**
- Action `MergeParties(User owner, Party $source, Party $target)`: same type, both active, source ≠ target; if the source's control-account balance is not zero, post one journal (source `party_merge`, `source_id` = target id, posting date = today) moving it to the target; source `status = inactive`, `merged_into_id = target`; audit `merged` on both. Purchases, sales and payments keep their original party.
- Page 20 `/parties/merge` (`party.merge`): pick source and target (same type), show both balances and the result, confirm.
- Target khata shows the merge row "Balance moved from {source name} ({code})" with a link to the source profile; the source profile shows "Merged into {target}".

**Rules:** BR-PTY-08.

**Tests (write first):** `AT-6` from `docs/acceptance/controls.json`; `T-15 merge leaves the source's journal lines untouched`; `merging a supplier into a buyer is refused`.

## T7.6 Backup status page

**Goal:** the Owner sees at a glance whether backups are running.

**Client requirement:** D-40; BR-SEC-08, BR-OPS-07; ADR-0006.

**Depends on:** T7.5.

**Build exactly:**
- No backup package. Backups are made by the server scripts `zb-backup-db` and `zb-backup-files` (`infra/`, protected), which write JSON status files into the folder `ZB_BACKUP_STATUS_DIR` (`config('zb.backup_status_dir')`, `config/zb.php`).
- `App\Domain\Backups\BackupStatus::read(): array` reads `backup-db.json`, `backup-db-last-success.json`, `backup-files.json`, `backup-files-last-success.json` (fields: `kind`, `result`, `finished_at` UTC, `file`, `bytes`, `copies`/`type`, `error`). Missing folder or file = "not configured on this server" (local development), never an exception.
- Page 48 `/settings/backups` (`backup.view`): for database and uploads: last successful backup (Asia/Karachi time, size in MB, copies made), last attempt result and error text, and a red "Late" badge when the last success is older than 2 hours (database) or 26 hours (uploads). A short fixed text: "Backups are encrypted and stored off the server. They can only be restored by the key holders." No download button (spec §7).
- Dashboard alert provider `BackupLate` (owner only) using the same rule.
- `README.md` section "Backups and restore" pointing to `docs/operations/runbook.md` §4 and §9 (do not copy the steps).

**Rules:** BR-SEC-08, BR-OPS-07.

**Tests (write first):** with fixture JSON files in a temporary folder: `fresh success shows OK`; `a success 3 hours old shows Late`; `a failure shows the error text`; `missing folder shows not configured`; `backup page requires backup.view`; `there is no download route`.

**Not in this task:** making or restoring backups (server scripts).

**Done when:** tests pass. **[Human]** after T8.3: one restore done on staging (runbook §4) and recorded in `docs/release-checks.md`.

## T7.8 Integrity check command

**Goal:** a daily, independent check that the books are whole, usable on live data and on a restored backup.

**Client requirement:** D-23; BR-OPS-08; ADR-0002.

**Depends on:** T7.7.

**Build exactly:**
- The checks live in `App\Domain\Ledger\IntegrityCheck` (inside the Ledger module, so the architecture rule on journal models allows it); the artisan command `zb:verify {--db-name=}` (`App\Console\Commands\VerifyLedger`) only calls it and prints the result. With `--db-name`, it points the `pgsql` connection at that database for this run only (`config([...])` + `DB::purge('pgsql')`), so `zb-restore --verify` can check a restored copy. Read-only: it never writes to the checked database.
- Checks, each reported as OK or FAILED with the IDs involved (never names or amounts in the log):
  1. every journal entry balances (debit total = credit total);
  2. trial balance totals are equal (T1.10 query);
  3. voucher numbers have no gaps and no duplicates for every document type, up to `next_number − 1`;
  4. every journal line on a control account (ledger account with `party_type`) has a `party_id`, and no other line has one;
  5. every active posted entry's `journal_entry_id` points to a journal whose `source_type`/`source_id` is that entry; every cancelled posted entry has a reversal journal.
- Exit code 0 when all pass, 1 otherwise.
- After a run on the live database (no `--db-name`), write `storage/app/zb-verify.json`: `{"result":"ok"|"failed","finished_at":"<UTC>","failed_checks":[...]}`. Write it with `json_encode` and no pretty printing: the server check looks for the exact text `"result":"ok"`. `zb-health-check` on the server reads this file and alerts when it says failed or is older than 26 hours.
- Schedule in `routes/console.php`: `zb:verify` daily at 20:30 UTC (01:30 Pakistan time), `withoutOverlapping()`.

**Rules:** BR-OPS-08.

**Tests (write first)** (`T-20`): after AT-1 every check is OK and the file says ok; planting each fault inside the test (disable the triggers for the test only, as the test role) makes exactly that check fail: an unbalanced journal, a voucher gap, a control-account line without party, an active entry pointing to another entry's journal; `--db-name` checks the named database.

**Not in this task:** fixing any fault automatically (never: faults are investigated by a person, runbook §5).

**Done when:** tests pass; the schedule is listed by `php artisan schedule:list`.
