## T1.1 Companies and company scope

**Goal:** every business record belongs to a company and every query is filtered by the user's company.

**Client requirement:** D-37.

**Depends on:** T0.3.

**Build exactly:**
- Migration `create_companies_table`: `id`, `name` varchar(150) not null, timestamps.
- Migration `add_company_and_active_to_users_table`: `company_id` bigint FK companies not null, `is_active` boolean not null default true. Existing kit users get the seeded company.
- `App\Domain\Companies\Models\Company`.
- Trait `App\Support\Tenancy\BelongsToCompany`: adds a global scope filtering by `auth()->user()->company_id` when a user is logged in, and fills `company_id` on `creating` from the logged-in user (or from an explicitly set value in console/seeders). Never applied to `User` itself.
- `CompanySeeder`: creates one company named "ZB Poultry Protein Mill" **only when no company exists** (running it twice never makes a second company).
- `SystemDataSeeder` (BR-OPS-11): the seeder that servers run on every deploy (`zb-deploy-release` calls `php artisan db:seed --class=SystemDataSeeder --force --database=pgsql_migrator`). In this task it calls only `CompanySeeder`; T1.2, T1.3, T1.4 and T2.3 each add their own system seeder to it. It must only add missing rows, never change existing data, never create users or test data, and be safe to run any number of times.
- `DatabaseSeeder` (local and tests only), replacing the kit's version:
  - first line: when `app()->environment('production')`, throw `RuntimeException('DatabaseSeeder is for local use. Servers use SystemDataSeeder.')`;
  - calls `SystemDataSeeder`;
  - keeps the kit's test user `Test User` / `test@example.com` (factory password `password`), created only if missing, in the seeded company.
- `UserFactory`: fills `company_id` with the first company, running `CompanySeeder` when none exists, so the kit's own tests keep passing.
- Login: a user with `is_active = false` cannot log in. Message: "This account is disabled. Ask the owner." (BR-USR-03).

**Rules:** BR-GEN-01, BR-USR-03 (login part), BR-OPS-11 (part).

**Tests (write first):**
- `BR-GEN-01 records of another company are invisible`: create a temporary table and model inside the test that uses the trait; insert rows for company A and B; logged in as a user of A, the query returns only A's rows.
- `BR-GEN-01 company_id is filled from the logged-in user on create`.
- `BR-USR-03 disabled user cannot log in`.
- `BR-OPS-11 SystemDataSeeder can run twice without creating a second company`.
- `BR-OPS-11 DatabaseSeeder refuses to run in production` (set `app()['env'] = 'production'` inside the test).
- `local DatabaseSeeder creates test@example.com in the seeded company`.

**Not in this task:** settings, roles, any business table.

**Done when:** tests pass; every later business model uses `BelongsToCompany`.

**Build exactly:**

## T1.7 Posting Service

**Goal:** the single place that writes journals, enforcing balance and party rules.

**Client requirement:** D-23; spec §6, §8.

**Depends on:** T1.4, T1.5, T1.6.

**Build exactly:**
- `composer require brick/money` (brings `brick/math`).
- `App\Support\Decimal` per `docs/conventions.md` §3 (with unit tests).
- `App\Domain\Ledger\PostingLine` and `PostingRequest` (readonly classes) per conventions §6.
- `App\Domain\Ledger\PostingService`:
  - `post(PostingRequest $r, User $by): JournalEntry`
    1. requires an open DB transaction;
    2. resolves each line's account (by code or id, must be active and in the company);
    3. checks: at least 2 lines; each amount is a positive 2-decimal string; total debit = total credit using `Decimal` (BR-LED-03); BR-LED-04 party rule: a line on an account with `party_type` must have a `party_id` whose party type matches (checked in T2.4 once parties exist; until then a party_type account with a null party is refused), and a line on any other account must have `party_id = null`;
    4. sets the posting flag, creates the entry with `entry_no` from `VoucherNumberService::next('journal')`, then the lines with `line_no` 1..n;
    5. runs `SET CONSTRAINTS journal_balance_check IMMEDIATE`, clears the flag, returns the entry.
  - `reverse(JournalEntry $original, string $postingDate, string $description, User $by): JournalEntry` posts the same lines with debit and credit swapped and `reversal_of_id = original.id`. A journal can be reversed only once (second attempt throws).
  - `isPosting(): bool`.
- `App\Domain\Ledger\PostingRules` class with **empty** method stubs for PR-01 … PR-27, each with the doc comment from spec §8.3, each throwing `LogicException('Not built yet: PR-xx')`. Each later task fills in its rules.

**Rules:** BR-LED-02, BR-LED-03, BR-LED-04 (account side), BR-LED-05.

**Tests (write first):**
- `BR-LED-03 an unbalanced request is refused before touching the database`.
- `PostingService posts a balanced two-line journal with JV-000001`.
- `BR-LED-05 reverse swaps every line and nets each account to zero`.
- `a journal cannot be reversed twice`.
- `BR-LED-04 a line on 2000 without a party is refused; a line on 5000 with a party is refused`.
- `Decimal::amount rounds half up`: kg `"0.005"` × rate `"1"` = `"0.01"` with `two_decimals`; kg `"812.5"` × rate `"52.5"` = `"42656.25"`; with `whole_rupee`, `"100.5"` × `"1"` = `"101.00"`.

**Not in this task:** period checks (T1.9), any specific posting rule body.

**Done when:** tests pass; arch test confirms only the Ledger module touches journal models.

## T1.10 Trial balance query

## T1.12 Security baseline

**Goal:** the security rules that apply to every page are in place before any screen is built.

- `AppServiceProvider`: `Model::shouldBeStrict(! app()->isProduction())`.
- `config/filesystems.php`: disk `local` gets `'serve' => false` and `'permissions' => ['file' => ['public' => 0640, 'private' => 0640], 'dir' => ['public' => 0750, 'private' => 0750]]`.

**Rules:** BR-SEC-04, BR-SEC-09, BR-SEC-13, BR-SEC-14, BR-SEC-15, BR-SEC-16, BR-SEC-17, BR-USR-08.

**Tests (write first):**
