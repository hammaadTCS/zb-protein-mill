# Environments

Five places the code runs, what each one is for, and every setting that differs between them. The database is **MariaDB 11.8 everywhere** with the same connection settings (conventions §14), so a query that passes in a cloud session or CI behaves the same on the host.

## 1. The five environments

| | Claude cloud session | Your laptop | CI (GitHub Actions) | Staging (Hostinger subdomain) | Production (Hostinger account) |
| --- | --- | --- | --- | --- | --- |
| Purpose | Claude builds one task and opens a pull request | You pull merged work, run it, check screens; you make `[spec-change]` edits | Checks every pull request and every push to `main`; builds releases | Client checks a release; monthly restore test | Real use |
| Data | Seeded test data | Seeded test data | Test data, thrown away | **Test data only** (G-19) | Real |
| OS | Ubuntu 24.04, PHP 8.3 | Linux Mint 22 (Ubuntu 24.04 base), PHP 8.3 | Ubuntu 24.04, PHP 8.3 and 8.5 | Hostinger shared hosting, PHP 8.5 (LiteSpeed) | Hostinger shared hosting, PHP 8.5 (LiteSpeed) |
| Database | MariaDB 11.8, started with `zb_mill_test` and `zb_mill_dev` by `scripts/cloud-session-start.sh` | MariaDB 11.8, `zb_mill_test` and `zb_mill_dev` from `scripts/setup-local.sh` | MariaDB 11.8 (`mariadb:11.8` service container) | MariaDB 11.8, its own database (`<prefix>_zb_mill_staging`), test data only | MariaDB 11.8, its own database (`<prefix>_zb_mill`) |
| DB login | one user (test values) over TCP | same | same | **one database user with a password** (D-43) | **one database user with a password** (D-43) |
| `APP_ENV` | `local` (tests: `testing`) | `local` (tests: `testing`) | `testing` | `production` | `production` |
| `ZB_ENV_NAME` | — | — | — | `staging` (yellow banner, T1.12) | `production` |
| `APP_DEBUG` | `true` | `true` | `false` | `false` | `false` |
| Secrets | **none, ever** (anyone using the cloud environment can read its variables) | **none real, ever** | none | own `APP_KEY`, own database password, own storage key, own monitor URLs | own set (`docs/secrets.md`) |
| Who deploys | — | — | — | You (`infra/hostinger/ship-release.sh` → `zb-deploy-release`) | You, after staging is approved |

Staging runs with `APP_ENV=production` on purpose, so it behaves exactly like live (password rules, error pages, caching). `ZB_ENV_NAME` is the only difference. Staging is a **second subdomain on the same Hostinger plan**, with its own database and test data only (D-9); production is the Hostinger account itself.

## 2. Settings (`.env`) by environment

Cloud sessions, the laptop and CI use `.env.example` (created in T0.1 from the kit's file) copied to `.env` with a fresh test `APP_KEY`; CI overrides the database name with `zb_mill_test`. The host uses `~/accounts/shared/.env`, created from `.env.production.example` over SSH when the account is set up.

| Key | Cloud / laptop / CI | Staging / production | Why |
| --- | --- | --- | --- |
| `APP_NAME` | `"ZB Poultry Protein Mill"` | same | Shown in titles |
| `APP_ENV` | `local` | `production` | See above |
| `ZB_ENV_NAME` | unset | `staging` / `production` | Banner and backup file names |
| `APP_KEY` | generated by `php artisan key:generate` | generated on the host (S-01) | Encryption |
| `APP_PREVIOUS_KEYS` | empty | empty except during a key change | Key rotation |
| `APP_DEBUG` | `true` | `false` | Never show stack traces to users (BR-SEC-16) |
| `APP_URL` | `http://localhost:8000` | `https://<domain>` | Links, cookies |
| `LOG_CHANNEL` / `LOG_STACK` | `stack` / `single` | `stack` / `daily` | Rotated files on the host |
| `LOG_LEVEL` | `debug` | `warning` | Less noise, less data (BR-SEC-17) |
| `LOG_DAILY_DAYS` | — | `14` | Retention |
| `DB_CONNECTION` | `mysql` | `mysql` | MariaDB everywhere, never SQLite (ADR-0013) |
| `DB_HOST` | `127.0.0.1` | `localhost` | The host's database server |
| `DB_PORT` | `3306` | `3306` | Default MariaDB port |
| `DB_DATABASE` | `zb_mill_dev` (tests: `zb_mill_test` from `phpunit.xml`) | `zb_mill` (staging: `zb_mill_staging`) | The host prefixes the name with the account name |
| `DB_USERNAME` | `zb_test` | `zb_app` | **One** database user with all rights on its own database (D-43, ADR-0014) |
| `DB_PASSWORD` | `local_test_only` | a strong random value | The only database password; kept in `.env` outside the web folder (BR-SEC-12) |
| `SESSION_DRIVER` | `database` | `database` | ADR-0004 |
| `SESSION_LIFETIME` | `60` | `60` | BR-SEC-04 |
| `SESSION_ENCRYPT` | `false` | `true` | BR-SEC-15 |
| `SESSION_SECURE_COOKIE` | unset (HTTP locally) | `true` | Cookie only over HTTPS |
| `SESSION_SAME_SITE` | `lax` | `lax` | |
| `CACHE_STORE` | `database` | `database` | ADR-0004 |
| `QUEUE_CONNECTION` | `sync` | `sync` | No worker (ADR-0004) |
| `MAIL_MAILER` | `log` | `log` | No e-mail in version 1 |
| `CSP_ENABLED` | `false` (Vite dev server) | `true` | BR-SEC-14 |
| `ZB_BACKUP_STATUS_DIR` | unset | `~/accounts/shared/status` | Backup page (T7.6) and `zb:backup` status files |

There is **no separate migration connection and no second database user** (`DB_MIGRATOR_USERNAME` is gone, D-43): the host gives one user with all rights on its own database only. The application still enforces the connection settings on every connection in `config/database.php` — `READ COMMITTED`, strict `sql_mode` with `ONLY_FULL_GROUP_BY`, `time_zone = '+00:00'`, engine `InnoDB`, `utf8mb4`/`utf8mb4_unicode_ci` (conventions §14, T10.1) — because the host's own server defaults have no strict mode and no `ONLY_FULL_GROUP_BY`.

## 3. Changing a setting on the host

1. Edit `~/accounts/shared/.env` over SSH (it is **outside** `public_html`; check the mode is `0640` afterwards).
2. `php artisan config:cache` (rebuilds the config cache), then reload by touching `~/accounts/current/public/index.php` or waiting for the next request.
3. Write what you changed and why in `docs/release-checks.md` (no secret values).

The configuration is cached on the host: editing `.env` without step 2 changes nothing. There is no root access and no server operating system to manage; hPanel holds the account, cron, database and certificate settings.

## 4. Business settings are not environment settings

Approval limits, formats, start date and the other OPEN values (spec §4, §9.6) live in the **database** and are entered by the Owner on the Settings page. They are never in `.env` and never in code. Tests use the test values in `docs/conventions.md` §11 only.
