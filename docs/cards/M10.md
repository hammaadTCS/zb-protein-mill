# M10: Run on Hostinger shared hosting (MariaDB)

The business moves the live system to its existing Hostinger "Unlimited" shared hosting account, so the
database engine changes from PostgreSQL to MariaDB (the MySQL family). **Every entry, rule, screen, report
and number stays exactly as built**; only the database engine and the server-side mechanics change. Spec
update 9.

**Owner's decisions (15 October 2026):**
- Backups are **daily (kept 35 days) + monthly (kept 7 years)**, not hourly. The honest recovery figure is
  "at most one day of entries can be lost"; accepted by the owner for a startup.
- **No separate written partner approval is needed:** both partners are the developers (CS graduates,
  university mates) and both know the change; the approval step of spec §20.3 is replaced by this note.
- The **books-fingerprint feature (T10.4) is deferred.** The paper register, kept by pen, is the real
  legal book; the digital copy needs no tamper-proof proof of its own. It can be added later as one task.

**Facts from the account check (15 October 2026, version 1):** MariaDB 11.8.9-log, InnoDB,
`utf8mb4`/`utf8mb4_unicode_ci`; **triggers work** (all 7 ledger-protection tests passed and
`mariadb-dump` keeps them); exact `DECIMAL` maths; transactions, `CHECK` and foreign keys enforced;
PHP 8.5.11 (CLI and web, LiteSpeed), opcache, sodium, `proc_open` all present; the app runs from a folder
outside `public_html`; security headers work; Backblaze B2 and healthchecks.io reachable. Server
defaults that matter: **one database user with all rights on its own database only**; `sql_mode` without
strict mode or `ONLY_FULL_GROUP_BY`; binlog off; `trust_function_creators` off.

## T10.1 The same MariaDB everywhere

**Goal:** the laptop, cloud sessions, CI and the host run the same database version and the same
connection settings, so a query that passes in tests behaves the same in production.

**Build exactly:**
- `config/database.php`: the `mysql` connection becomes the default. The session settings are **enforced
  by the app**, never trusted from the server: `READ COMMITTED` isolation, `sql_mode` =
  `STRICT_TRANS_TABLES,ERROR_FOR_DIVISION_BY_ZERO,NO_AUTO_CREATE_USER,NO_ENGINE_SUBSTITUTION,ONLY_FULL_GROUP_BY`,
  `time_zone = '+00:00'`, `utf8mb4`/`utf8mb4_unicode_ci` default collation, InnoDB engine
  (`engine` option set / `utf8mb4` charset in the connection).
- A startup check (`zb:verify` extended, or a new `zb:db-check` run by it and by the scheduler) that
  **refuses to run the system** on: MariaDB older than 10.2 (`CHECK` silently ignored), a table that is
  not InnoDB, a session `sql_mode` without strict mode, a wrong connection time zone, or a missing
  trigger. Message names the failing item; run on boot and by `zb:verify`.
- `phpunit.xml`, `.env.example`, `.env.production.example`: `mysql` connection and MariaDB credentials
  shape; the test database name.
- `scripts/cloud-session-start.sh` (installs and starts MariaDB 11.8 in the cloud session with the same
  settings), `scripts/setup-local.sh` (MariaDB 11.8 on the laptop), `.github/workflows/ci.yml` (service
  container `mariadb:11.8` with the same settings).
- **Version of record: MariaDB 11.8** (exactly what the host runs) — laptop, cloud, CI and production.

**Tests:** `DbSettingsTest` (the connection reports `READ COMMITTED`, strict `sql_mode`, `+00:00`, InnoDB,
InnoDB engine); the guard test for the startup check (a fake bad setting is refused).

**Done when:** the existing suite boots against MariaDB with the PostgreSQL code still in place except
what T10.2 forces (migrations switch in T10.2, so this task ends with a migrated database and the app
booting); the full suite goes green in T10.3.

**Not in this task:** the migrations themselves (T10.2) and the query rewrites (T10.3).

## T10.2 Migrations and database rules (33 migration files)

**Goal:** the schema, indexes and database-level protections are rebuilt for MariaDB, with the same
behaviour and the same refusal messages.

**Depends on:** T10.1.

**Build exactly:**
- `timestampTz` → `DATETIME(3)`, always UTC (15 migration files use it); the connection time zone is
  `+00:00` (T10.1), so `now()`/`UTC_TIMESTAMP()` agree.
- The 2 partial unique indexes (opening balances) → plain unique indexes on the nullable column (MariaDB
  allows many `NULL`s in a unique index); a test proves the same behaviour (Q-8).
- `gen_random_uuid()` on the 13 `public_id` columns (available on MariaDB 11.8; verify in T10.1,
  fallback `UUID()`).
- Unique-rule columns get **binary collation** (`utf8mb4_bin`): party/account/item/category names,
  codes, e-mails, voucher numbers, idempotency keys. Search columns (`name_ur`, notes, references) keep
  `utf8mb4_unicode_ci`. A test re-proves the duplicate rules: "Aslam" ≠ "aslam" ≠ "Aslam " (Q-6).
- **Rewrite every `prevent_change()` / `prevent_delete()` trigger in MariaDB syntax**
  (`SIGNAL SQLSTATE '45000'`), the same tables and the same behaviour (BR-SEC-11); the existing refusal
  tests pass unchanged.
- **The seal row replaces the deferred constraint trigger** (new rule **BR-LED-10**): new table
  `journal_seals` (one row per journal entry); a `BEFORE INSERT` trigger on `journal_seals` sums that
  entry's `journal_lines` and refuses (`SIGNAL`) when there are fewer than two lines or debit ≠ credit.
  `PostingService` inserts the seal row at the end of its saving transaction, where today it runs
  `SET CONSTRAINTS … IMMEDIATE`. The BR-LED-03 guarantee stays **inside the database**.
- **No** `pgsql_migrator` role: the check report shows one all-rights database user, so the two-user
  split (D-3) cannot be made; documented as accepted by both owners (they are the developers), with the
  daily `zb:verify` books check, off-site backups and the paper register as the compensating controls.
- `PostingService::isPosting()` model guards and the posting flag stay.

**Tests:** every schema-refusal test (edit and delete refused on the protected tables, unbalanced entry
refused by the seal trigger, opening-balance duplicate refused); the 7 check scripts of the account report
pass against the real schema; `migrate:fresh --seed` on MariaDB.

**Done when:** the above tests pass; the seal trigger refuses an entry with one line and an entry whose
debits do not equal its credits.

**Not in this task:** the query rewrites (T10.3) and removing PostgreSQL (also T10.3).

## T10.3 Queries: the PostgreSQL-only SQL, and the stop-gate

**Goal:** every query gives **the same answer to the paisa and the same rows in the same order** as on
PostgreSQL today, and only then is PostgreSQL removed.

**Depends on:** T10.2.

**Build exactly (file by file):**

| File(s) | Today (PostgreSQL) | On MariaDB |
| --- | --- | --- |
| 8 controllers with search (Purchase, Sale, Payment, Expense, Transfer, Party, PartnerTransaction, search) | `ilike` | `LIKE` (case handled by the column's case-insensitive collation) |
| 12+ files (`PurchaseController`, `SaleController`, `PaymentController`, `ExpenseController`, `TransferController`, `PartnerTransactionController`, `Party.php`, `EntrySlip`, `PartnerStatement`, `AccountStatement`, `PendingBalances`, `DailySummary`, `DashboardToday`, `BusinessInsights`, …) | `::numeric(…)::text` casts | `CAST(… AS DECIMAL(…))`, the **same precision**, so the result strings stay byte-identical |
| `PartnerStatement`, `PaymentController`, `PartnerTransactionController`, `DashboardToday`, `BusinessInsights` | `SUM(…) FILTER (WHERE …)` | `SUM(CASE WHEN … THEN … END)` |
| `BusinessInsights` | `to_char(entry_date, 'YYYY-MM')` | `DATE_FORMAT(entry_date, '%Y-%m')` |
| `Ageing.php` | CTE `(VALUES …)`, `?::date - date`, window sums with date subtraction | `UNION ALL` selects instead of `VALUES`, `CAST(? AS DATE)`, `DATEDIFF()` (Q-1: **`20261101 − 20261031 = 70` on MariaDB** — silently wrong without the fix); the PHP match-based paths (proved equal in T9.2) become the oracle |
| `AccountStatement.php` | window `SUM(…) OVER (… ROWS UNBOUNDED PRECEDING)` cast to numeric | the same window on MariaDB + `CAST`; the test compares it with the PHP running balance |
| `Periods.php` | `pg_advisory_xact_lock_shared` / `pg_advisory_xact_lock` | one `company_locks` row per company; `FOR SHARE` / `FOR UPDATE` inside the same transaction (MariaDB 11.8 supports `FOR SHARE`), released at commit/rollback exactly like the advisory lock |
| `PostingService.php` | `SET CONSTRAINTS journal_balance_check IMMEDIATE` | the seal-row insert (T10.2) |
| `VoucherNumberService.php` | `insertOrIgnore` (was `ON CONFLICT DO NOTHING`) | keep `INSERT IGNORE` but add the duplicate-key catch from `Idempotency`, or use `INSERT … ON DUPLICATE KEY UPDATE`; the T-04 race test must pass |
| `IntegrityCheck.php`, `VerifyLedger.php`, `Idempotency.php` | PostgreSQL SQLSTATE `23505`, raw selects | MariaDB codes (`1062` / SQLSTATE `23000`), ported raw SQL, **the same output text** |
| every raw `now()` | — | verified per file; the UTC connection keeps `now()`/`UTC_TIMESTAMP()` consistent |

**Stop-gate — all three must pass before PostgreSQL is removed:**
1. The full suite (588+ tests) green on MariaDB 11.8.
2. **Same-answer check:** the acceptance world (AT-1…AT-6, `controls.json`) is loaded into PostgreSQL
   (old code) and MariaDB (new code); every report, khata, statement, trial balance, ageing, dashboard
   figure and PDF data is generated on both and compared line by line. Any difference stops the task
   until explained and fixed.
3. Only after 1 and 2: remove PostgreSQL — the `pgsql` connection, `pgsql_migrator`, the T1.11 test,
   Postgres-only branches in the scripts and CI's Postgres service; `infra/files/postgres/` is moved to
   `infra/history/`.

**Existing tests that change:** only `tests/Support/AcceptanceRunner.php` — its four PostgreSQL
`::numeric` / `::text` casts (lines ~398–415) become `CAST(… AS DECIMAL(14,3))` / `CAST(… AS CHAR)`.
Because that file is the same-answer oracle, the AT-1…AT-6 totals must stay byte-identical. Every
other existing test is expected to pass **unchanged** — stop-gate 1 is exactly that. The new
`tests/Feature/Security/MigratorConnectionTest.php` (BR-SEC-12, D-43) ships green in this patch.

**Tests:** all existing tests, plus the same-answer runner; the PHP match paths as the ageing oracle; the
`AccountStatement` window against the PHP running balance; the T-04 race test.

**Done when:** 1, 2 and 3 above are done and recorded in `docs/release-checks.md`.

## T10.5 Security headers in the app

**Goal:** every security header the VPS's nginx sent is set by the application itself (D-8), so shared
hosting needs no server-file configuration.

**Build exactly:** Laravel middleware (building on the existing CSP-with-nonce of T1.12) sets HSTS,
`X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, `X-Content-Type-Options` and the CSP. The
public `.htaccess` keeps only what the app cannot send. The nginx snippet `infra/files/nginx/snippets/zb-mill-headers.conf`
retires with the VPS files (kept under `infra/history/`).

**Tests:** `SecurityHeadersTest` (`curl -si`-equivalent: every header present on a web response).

**Done when:** the T8.1 "verify on staging" header rows are filled from staging.

## T10.6 Backups from PHP — daily and monthly (replaces the VPS scripts)

**Goal:** encrypted off-site backups with the owner's decided cadence, run from the application so shared
hosting needs no server timers.

**Owner's decision (15 October 2026): daily + monthly, not hourly.** The spec text changes with it:
BR-OPS-01 and BR-OPS-05 (see the spec patch) now say one **daily** backup and one **monthly** long-keep
copy, and the honest recovery figure is "at most one day of entries can be lost" (accepted by the owner).

**Build exactly:** an artisan command `zb:backup` that runs `mariadb-dump` (present on the host, triggers
included — proved by the account check) → gzip → encrypt with **sodium** to the storage's public key →
upload to Backblaze B2 with an upload-only key. Two kinds of copy, both driven by `schedule:run`:
- **Daily**, after the day's `zb:verify` (01:45 Pakistan time): full database + uploads; kept **35 days**.
- **Monthly** (1st of the month): full database + uploads; kept **7 years** (O-35 / Income Tax Ordinance).
- Naming and retention are done by the script itself, so nothing on the storage can delete a copy early
  (the storage user has upload rights only — the VPS-days design, unchanged).

Hostinger's own daily backups are an extra copy (D-4). A `zb:restore` command for staging/laptop is
proved by a real restore (fills the empty "Restore tests" table in `docs/release-checks.md`). A dead-man
ping to healthchecks.io (reachable, checked) plus the existing Backups page (T7.6) reading the same status
files, unchanged.

**Tests:** `BackupCommandTest` (dump → encrypt → upload against a fake endpoint; dead-man ping on success
and on failure; retention naming for daily and monthly); `zb:restore` round-trip on the test database.

**Done when:** the daily and monthly jobs run from the scheduler, a real backup restores on staging, and
`docs/release-checks.md` records the restore.

**Not in this task:** deploy and cron (T10.7).

## T10.7 Deploy, roll-back, scheduler

**Goal:** one-command deploy with a one-command roll-back on shared hosting.

**Depends on:** T10.6.

**Build exactly:**
- `releases/<version>/` folders + a `current` link; the subdomain's document root points at
  `current/public` (the check proves links outside `public_html` are served). Roll-back = repoint the
  link, one command.
- Migrations run over SSH after each release (Laravel's safe-migration rule is unchanged).
- hPanel cron every minute → `php artisan schedule:run` (H-2 to confirm); everything the system schedules
  already goes through the scheduler (`zb:verify`, backups).
- LiteSpeed notes in the runbook: the `.htaccess` from `public/`; no nginx files needed; the
  `trust_function_creators`/binlog dependency written down ("if trigger creation ever starts failing").
- New files under `infra/hostinger/` (deploy, health, backup glue); the VPS scripts move to
  `infra/history/` and stay as history.

**Tests:** `infra/tests` deploy and roll-back scripts against a fake layout.

**Done when:** a release deploys to staging from CI artifacts and rolls back, both one command.
