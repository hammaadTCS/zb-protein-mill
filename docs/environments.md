# Environments

Five places the code runs, what each one is for, and every setting that differs between them.

## 1. The five environments

| | Claude cloud session | Your laptop | CI (GitHub Actions) | Staging server | Production server |
| --- | --- | --- | --- | --- | --- |
| Purpose | Claude builds one task and opens a pull request | You pull merged work, run it, check screens; you make `[spec-change]` edits | Checks every pull request and every push to `main`; builds releases | Client checks a release; monthly restore test | Real use |
| Data | Seeded test data | Seeded test data | Test data, thrown away | **Test data only** (G-19) | Real |
| OS | Ubuntu 24.04, PHP 8.3 | Linux Mint 22 (Ubuntu 24.04 base), PHP 8.3 | Ubuntu 24.04, PHP 8.3 and 8.5 | Ubuntu 26.04, PHP 8.5 | Ubuntu 26.04, PHP 8.5 |
| PostgreSQL | 16, started with `zb_mill_test` and `zb_mill_dev` by `scripts/cloud-session-start.sh` | 16, `zb_mill_test` and `zb_mill_dev` from `scripts/setup-local.sh` | 18 (service container) | 18 | 18 |
| DB login | `zb_test` / `local_test_only` over TCP | same | same | peer auth, no password | peer auth, no password |
| `APP_ENV` | `local` (tests: `testing`) | `local` (tests: `testing`) | `testing` | `production` | `production` |
| `ZB_ENV_NAME` | — | — | — | `staging` (yellow banner, T1.12) | `production` |
| `APP_DEBUG` | `true` | `true` | `false` | `false` | `false` |
| Secrets | **none, ever** (anyone using the cloud environment can read its variables) | **none real, ever** | none | own `APP_KEY`, own storage key, own monitor URLs | own set (`docs/secrets.md`) |

Staging runs with `APP_ENV=production` on purpose, so it behaves exactly like live (password rules, error pages, caching). `ZB_ENV_NAME` is the only difference.

## 2. Settings (`.env`) by environment

Cloud sessions, the laptop and CI use `.env.example` (created in T0.1 from the kit's file) copied to `.env` with a fresh test `APP_KEY`; CI overrides the database name with `zb_mill_test`. Servers use `/srv/zb-mill/shared/.env`, created from `.env.production.example` by provisioning.

| Key | Cloud / laptop / CI | Staging / production | Why |
| --- | --- | --- | --- |

| `ZB_ENV_NAME` | unset | `staging` / `production` | Banner and backup file names |
| `APP_KEY` | generated by `php artisan key:generate` | generated on the server (S-01) | Encryption |

## 3. Changing a setting on a server

1. `sudoedit /srv/zb-mill/shared/.env` (keeps owner `zbdeploy`, group `zbmill`, mode 0640; check with `ls -l` afterwards).
2. `sudo zb-deploy-release --refresh-config` (rebuilds the config cache and reloads PHP).
3. Write what you changed and why in `docs/release-checks.md` (no secret values).

The configuration is cached on servers: editing `.env` without step 2 changes nothing.

## 4. Business settings are not environment settings

Approval limits, formats, start date and the other OPEN values (spec §4, §9.6) live in the **database** and are entered by the Owner on the Settings page. They are never in `.env` and never in code. Tests use the test values in `docs/conventions.md` §11 only.
